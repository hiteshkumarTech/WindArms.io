## 2026-07-31 (Step 8E-D.1)

- **Milestone 8, Phase G, Step 8E-D.1 — dev-only player-centered, texel-stabilized shadow frustum. `/v2/range?shadow=1&shadowReview=1` ONLY — no commit yet, human visual gate requested.** Directly answers Step 8E-D's own flagged architectural finding: `RANGE_SHADOW_CAMERA_BOUNDS`' full-floor (130m×130m) frustum makes texel density the real bottleneck, not bias/resolution. Step 8E-D.1A (measurement-only, prior pass) measured the real deformed-mesh light-space footprint across 13 action states and proposed a 3.5m×6m rectangular candidate (near 20/far 27); this pass implements tracking against that candidate. Does NOT begin Step 8E-E (production caster-ownership switch) — the visible FP arms remain the only shadow real players see today.
  - **New pure tracking module** (`playerCenteredShadowFrustum.ts`) — `PLAYER_CENTERED_SHADOW_FRUSTUM_CONFIG` (3.5×6.0m, map 1024², near 20/far 27) and `STATIC_FULL_FLOOR_SHADOW_FRUSTUM_CONFIG` (130×130m, restated from `RANGE_SHADOW_CAMERA_BOUNDS` for a shared shape, live-regression-tested against it). `snapToTexelGrid()` snaps a light-space anchor to the shadow map's own texel grid independently per axis (`3.5/1024 ≠ 6.0/1024` — a rectangular frustum cannot share one texel-size scalar across X/Y), deterministic and frame-rate-independent (absolute input → absolute output, no hidden state, no accumulation), fails soft to (0,0) on non-finite input. 15 tests.
  - **A real bug caught by its own unit test, not shipped**: the fixed light-space basis (`playerCenteredShadowFrustumBasis.ts`, `buildFixedLightSpaceBasis()`) was initially built from a plain `THREE.Object3D`. `Object3D.lookAt()` special-cases `isCamera || isLight` objects to use the standard -Z-forward camera convention, but uses the OPPOSITE, swapped-argument convention for a plain object (meant for e.g. an arrow mesh's +Z pointing at a target) — a real, easy-to-miss three.js behavior difference. Since THREE's actual `DirectionalLightShadow.camera` is a real `OrthographicCamera` (uses the camera-convention branch), a plain-`Object3D` reference frame would have produced a MIRRORED basis relative to the real shadow camera — texel snapping would not have aligned with the real texel grid at all. Caught by a round-trip test asserting the canonical target's light-space Z (`(0,0,0)` should project to `(0,0,-26.31)` under the light-facing convention); the test failed with `+26.31` before the fix. Fixed by using a detached `THREE.Camera` instead — 9 new tests, including a same-axis-forward-translation-only-changes-Z proof.
  - **Ground anchor tracks `(player.x, 0, player.z)`, never the player's live/airborne Y** — the fixed Y (0) is the canonical light target's own original Y (light target = world origin pre-8E-D.1), chosen specifically because it preserves the canonical light-to-target geometry exactly along the vertical axis while only translating horizontally to follow the player. Confirmed live: ground-anchor Y stayed exactly 0.00 and light-world Y stayed exactly 22.00 across a full jump→fall→landing arc.
  - **Imperative controller** (`KaelPlayerCenteredShadowController.tsx`) is the sole owner of the light's `position`, its explicit target's `position`, and the shadow camera's bounds while mounted (review mode only) — reads `getFirstPersonBodyWorldPose()` (the same existing bridge the review camera/receiver/shadow body already use, no new position store), projects into the fixed basis, snaps, reconstructs, and updates light/target as absolute world positions every frame (never incremental deltas). `light.shadow.camera.updateProjectionMatrix()` is called only on an actual mode transition, not every frame. An always-present explicit target `Object3D` (rather than conditionally attached) is byte-identical to THREE's own implicit default (world origin) whenever nothing is actively moving it — this is what makes both "normal `/v2/range` unchanged" and "no stale target left behind on flag disable" true simultaneously; an unconditional unmount-cleanup effect additionally restores canonical light/target/bounds regardless of what mode was active, independent of React/R3F prop-diffing behavior.
  - **`shadowReviewStore.ts` extended** with `frustumMode` (`'static-full-floor' | 'player-centered'`, defaults to `player-centered` — the canonical candidate for human review, static kept one click away for direct A/B) and `showFrustumHelper` (a `THREE.CameraHelper` wireframe toggle, `KaelShadowFrustumHelper.tsx`, defaults OFF, absent from marker-free captures — lives in the non-calibration default group since it's a pure visualization aid). 11 new store tests.

  - **A real finding from implementing the production mode**: the real range floor (`STORM.abyss`) is dark enough under the scene's current ambient/hemisphere/directional light levels that a cast shadow reads with genuinely LOW contrast against it — confirmed by direct comparison, not assumed. This isn't a bug introduced this pass; it's a pre-existing characteristic of the production floor's own darkness, now visible for the first time because no prior pass compared the shadow prototype against a receiver this dark. The `readable` mode exists specifically because tuning/defect-spotting against a receiver where the shadow is barely visible is not practical.

Left disabled, per the brief's own "enable only when screenshots demonstrate a meaningful improvement" rule.

  - **22 new tests** (`shadowLightCalibration.test.ts`, 14; `shadowReviewStore.test.ts` additions, 8) covering: bounded-range validators (accept-at-bounds, reject-just-outside, reject-non-finite), permitted-map-size allowlist, production receiver uses the real `STORM.abyss` token, readable receiver preserves original values, canonical-calibration finiteness, `resetCalibration()` vs `reset()` field-set independence, invalid setter input is rejected (store unchanged, not clamped or thrown). `typecheck`/`test` (449/449, up from 427)/`lint`/`build` all clean.
